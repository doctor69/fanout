Fanout setup

Platform keys

Every platform needs your app registered before it will show a user a consent screen. Six registrations, one per platform — plus one extra from Google if you build for iOS as well. Your users never see any of this.

01

YouTube

Google Cloud Console · about 10 minutes

No server needed No review Video only
Start here. It's the only platform with nothing standing between you and a real post — no secret, no server, no approval. If something is structurally wrong, YouTube tells you in ten minutes instead of two weeks.
  1. Open console.cloud.google.com and create a project.
  2. APIs & Services → Library → search YouTube Data API v3 → Enable.
  3. OAuth consent screen → External. Add the scope: 
    https://www.googleapis.com/auth/youtube.upload
    Add your own Google account under Test users. Skip this and sign-in is refused while the app is unverified. It's the single most common stumble here.
  4. Get the SHA-1 of your debug signing key — the next step asks for it: 
    keytool -list -v -keystore ~/.android/debug.keystore \
  -alias androiddebugkey -storepass android -keypass android | grep SHA1
  5. Credentials → Create credentials → OAuth client ID, type Android. Package name: 
    com.fanout.app
    Paste the SHA-1 from the previous step.
  6. Open that client's Advanced Settings and enable the custom URI scheme method.
    Google now disables custom URI schemes for new Android clients by default. Without this, the redirect back to fanout:/oauth/youtube is rejected and the browser hangs on a Google error page.
  7. Copy the client ID — it ends in .apps.googleusercontent.com — into app/.env: 
    EXPO_PUBLIC_GOOGLE_CLIENT_ID=
Building for iOS too? Google issues a separate client per platform and neither works on the other. You'll need a second, iOS-type client — see Also running on iOS below.
02

X

X developer portal · about 10 minutes

No server needed No review Video + photo
  1. Open developer.x.com → create a project, then an app inside it.
  2. In the app's User authentication settings, turn on OAuth 2.0 and set the type to Native App — that makes it a public client using PKCE, with no secret to leak.
  3. Callback URI: 
    fanout:/oauth/x
  4. App permissions: Read and write. Posting needs both tweet.write and media.write; read-only silently fails later.
  5. Copy the Client ID (not the API key) into app/.env: 
    EXPO_PUBLIC_X_CLIENT_ID=

That's both of the platforms that work entirely from the phone. The remaining four all demand a client secret to complete the token exchange, and a secret can never ship inside an app — anyone can unzip an APK. So they share one small serverless function. Deploy it once, then they all work.

Shared prerequisite

Deploy the token-exchange function

A Cloudflare Worker that swaps an auth code for a token using the secret, and stores nothing. Free tier covers this many times over. It is not a backend for the app — no user data lives there. 

cd functions
npx wrangler login
npx wrangler secret put TIKTOK_CLIENT_SECRET
npx wrangler secret put META_APP_SECRET
npx wrangler secret put LINKEDIN_CLIENT_SECRET
npm run deploy

Then put the deployed URL in app/.env:

EXPO_PUBLIC_TOKEN_EXCHANGE_URL=https://fanout-token-exchange.<you>.workers.dev
Add each secret as you register that platform below — you don't need all three up front. wrangler secret put can be re-run any time.
03

TikTok

TikTok for Developers · registration ~20 min, then a wait

Needs the Worker App audit: 1–2 weeks Video only
  1. Open developers.tiktok.com, register as a developer, and create an app.
  2. Add both products: Login Kit and the Content Posting API. Request the video.publish scope — without it the app signs in but cannot post.
  3. Redirect URI: 
    fanout:/oauth/tiktok
  4. Copy the client key (TikTok's name for the public ID) into app/.env: 
    EXPO_PUBLIC_TIKTOK_CLIENT_KEY=
  5. Put the client secret on the Worker — never in .env: 
    cd functions && npx wrangler secret put TIKTOK_CLIENT_SECRET
  6. Submit for app audit when you're ready to post publicly. It wants a privacy policy URL and a demo video of the whole sign-in and upload flow.
Before the audit passes, posts are private-only. That's TikTok's rule for unaudited apps, not a bug. Fanout already handles it: it asks TikTok which privacy levels your account may use and takes the most public one offered — so the same code starts posting publicly the day approval lands, with no change.
Photos won't work here at all. TikTok photo posts accept only a publicly hosted image URL, which a file on a phone isn't. Video posts are unaffected.
04

Instagram + Facebook

Meta for Developers · one app covers both

Needs the Worker App Review Needs a Facebook Page
  1. Open developers.facebook.com → create an app of type Business.
  2. You need a Facebook Page — Fanout posts to a Page, never to a personal profile. For Instagram, a Business or Creator account linked to that same Page.
  3. Add Facebook Login, and under its settings add both redirect URIs: 
    fanout:/oauth/facebook
fanout:/oauth/instagram
  4. Copy the App ID into app/.env: 
    EXPO_PUBLIC_META_APP_ID=
  5. Put the App Secret on the Worker: 
    cd functions && npx wrangler secret put META_APP_SECRET
  6. Submit for App Review before real users can connect. Until then it works only with accounts listed as testers on the app.
If Meta rejects the redirect: it has historically wanted https URLs for the web OAuth dialog rather than a custom scheme. If fanout:/oauth/facebook is refused, the fix is a small bridge route on the Worker you already deployed that redirects back to the app scheme. Ask and it can be added.
Instagram photos need a public URL — same constraint as TikTok. Instagram video posts upload fine as Reels; Facebook takes both photos and video directly.
05

LinkedIn

LinkedIn Developers · about 15 minutes

Needs the Worker Company page required Video + photo
  1. Open linkedin.com/developers → create an app. It must be associated with a LinkedIn company page — create a throwaway one if you don't have it.
  2. On the Products tab, request both Sign In with LinkedIn using OpenID Connect and Share on LinkedIn. Posting needs the second one.
  3. Under Auth, add the redirect URL: 
    fanout:/oauth/linkedin
  4. Copy the Client ID into app/.env: 
    EXPO_PUBLIC_LINKEDIN_CLIENT_ID=
  5. Put the Client Secret on the Worker: 
    cd functions && npx wrangler secret put LINKEDIN_CLIENT_SECRET

Second platform

Also running on iOS

One codebase covers both, so this is mostly verification rather than new work. Two things actually differ: what it costs, and Google.

It's free

Xcode and the iOS Simulator are free, and a Simulator build needs no code signing at all — no Apple ID, no enrolment. What it needs is a Mac; Xcode runs nowhere else.

The $99/year Apple Developer Program only becomes necessary for TestFlight, the App Store, or installing on someone else's device. You can run your own iPhone on a free Apple ID too — the build just expires every 7 days and has to be re-installed.

Google needs a second client ID

An Android client is bound to your package name and signing fingerprint; an iOS client to your bundle ID. They're different strings and neither works on the other platform.

  1. Same Google Cloud project → Credentials → Create credentials → OAuth client ID, type iOS. Bundle ID: 
    com.fanout.app
  2. Keep them in separate variables — the app picks the right one at runtime: 
    EXPO_PUBLIC_GOOGLE_CLIENT_ID_ANDROID=
EXPO_PUBLIC_GOOGLE_CLIENT_ID_IOS=
If Google refuses the redirect on iOS: iOS clients conventionally use Google's reversed-client-ID scheme (com.googleusercontent.apps.<id>:/oauth2redirect) rather than fanout:. If the browser comes back with a redirect_uri error, say so — it's a small change to the YouTube flow plus one scheme entry in app.json. This one is untested so far.

The other five need nothing new

X, TikTok, Meta and LinkedIn issue one client ID that isn't tied to a platform, and the same fanout:/oauth/… redirect URIs you already registered work on iOS unchanged. No second registration, no extra variables.

Build and run it

cd app
npx expo run:ios

That prebuilds, runs pod install, builds, boots a Simulator and installs. The first pod install is slow — that's normal, not a hang.

Don't use Expo Go for the connect flows. Expo Go serves its own URL scheme, so the redirect back to fanout:/oauth/… never reaches the app and sign-in looks like it silently failed. The build above is fine.

The finished .env

app/.env — gitignored, never committed

Fill in only the platforms you've registered. Anything left blank shows as Set up on that row in the app and is simply skipped — the others keep working. 

EXPO_PUBLIC_GOOGLE_CLIENT_ID_ANDROID=
EXPO_PUBLIC_GOOGLE_CLIENT_ID_IOS=
EXPO_PUBLIC_X_CLIENT_ID=
EXPO_PUBLIC_TIKTOK_CLIENT_KEY=
EXPO_PUBLIC_META_APP_ID=
EXPO_PUBLIC_LINKEDIN_CLIENT_ID=
EXPO_PUBLIC_TOKEN_EXCHANGE_URL=
Restart with a cleared cache after every change. Metro bakes these values in at build time and will happily serve the old empty ones — you'll swear nothing happened. 
cd app && npx expo start --clear
No secrets in this file, ever. Everything here ships inside the app bundle where anyone can read it. That's fine — client IDs are public by design. Client secrets go on the Worker via wrangler secret put and nowhere else.
Progress ticks are stored in this browser only. Full written steps live in docs/connecting-accounts.md; every variable is also documented in app/.env.example.
